### Still open

- **PURGE-005 · A deletion the SWEEPER recovered was quietly less complete than one the callable finished — fixed, with one stated limit** — Codex P1 on #2228. `purgeUserData` was already shared, so the Firestore half matched. The two steps that are not Firestore — closing the web deletion request, and deleting the PostHog person and their events — lived inline in `accountCallableHandlers.js`, below `runAccountDeletion` and unreachable from the recovery path. So a deletion the cron finished left the analytics profile in place and reported `completed`, because from where it stood the purge had verified. The Privacy Policy §7 promise was kept on one path and not the other, invisibly.

  Fixed by `functions/account/accountPostPurgeCleanup.js` — one routine, both callers — with a source-scan guard (`test:purge-cleanup-parity`) that fails if either caller does cleanup inline again, and its twin that fails if a caller stops calling it at all. Both mutation-verified: without the pair, deleting the call entirely satisfies "no inline cleanup".

  **The stated limit.** `deletionRequests` rows are keyed by EMAIL and the sweeper has none — the Auth user is deleted before the purge starts and the tombstone deliberately stores only `hashEmail()`. Rows now carry that same hash so the sweeper can match them, but **a row written before that field existed cannot be matched and stays open for a human**. It is skipped rather than guessed at, and nothing reports it: the scan cannot tell "no open row for this person" from "a row that predates the field". Bounded and shrinking. PostHog has no such caveat — it is uid-keyed, so parity there is total.

  **Still unexercised in production**, like the rest of the recovery path.

- **PURGE-004 · Surviving-token inventory: what the deletion gate now covers, and what it does not** — recorded alongside the item-3 fix, because "we blocked the writes" is only true of the surfaces someone counted.

  **Covered.** `firestore.rules` and `storage.rules` both gained `notBeingDeleted()`, wired into the `isVerified()` chokepoint that ~167 Firestore rules and the Storage rules run through, and `functions/authGuard.js`'s `assertActiveAccount` now reads the tombstone alongside the status field. That closes client writes, uploads, and every callable or HTTP endpoint routed through the guard.

  **The reason it was open at all is worse than "unchecked", and worth keeping written down:** `notSuspended()` in the rules and `assertActiveAccount` in the guard BOTH fail open on a missing `users/{uid}` — deliberately, so legacy accounts predating the status field are not locked out. The purge DELETES `users/{uid}`. So the moment it did, both predicates started returning "fine" and the surviving token's access was effectively restored by the deletion itself.

  **The one collection the chokepoint did not reach, found by CI rather than by reading.** `users/{userId}` deliberately does not route through `isVerified()` — a signup writes its profile before the account is verified at all — so wiring the gate into `isVerified()` closed every collection except the single document whose return *is* the resurrection. `bootstrapUserProfile` already refuses a tombstoned uid (#2244), but that is a callable; a raw client `setDoc` from a surviving token never reaches it. The gate is now spelled out on both self-write branches, and asserted as text as well as behaviour so a local `test:all` catches its removal without an emulator. Worth generalising: **a chokepoint audit answers "what runs through it", not "what doesn't"** — the collections that bypass `isVerified()` are exactly the ones a gate added there cannot protect, and they are the interesting ones by construction.

  **Counted, not covered.** `functions/index.js` alone has **42 `onCall` and 4 `onRequest`** against **29 `assertVerifiedAuth` + 3 `assertDecodedVerified`** call sites, and 93 files under `functions/` contain an `onCall`. The shortfall is not all unguarded — several callables are deliberately exempt (`bootstrapUserProfile` is, by design, and now carries its own transactional tombstone check), some are admin-only behind a different guard, and some are unauthenticated by intent. **But nobody has enumerated which is which**, and a per-export audit is the only thing that turns this paragraph into a claim. Until that exists, the honest statement is: the chokepoint is closed, the surfaces that bypass the chokepoint are unaudited.

  **Also outside the gate:** three `getSignedUrl` call sites in `functions/`. A signed URL is a bearer credential that does not re-check rules or auth when redeemed, so one minted before a deletion stays usable for its lifetime regardless of the tombstone. Bounded by the URL's own expiry rather than by anything this fix does.

- **PURGE-003 · The client still skips `signOut` on a terminal deletion failure, and #2236 made it fire more often** — Codex P1 on #2228, still open, and now coupled to a change that shipped after it. `purge-failed` / `purge-unverified` / `purge-incomplete` all reject *after* the Auth user is gone, and `accountService` skips its `signOut` block on rejection, so the deleted user sits on the dashboard until a token refresh happens to expire the session. #2236 widened the branch that reaches it: previously only an unverified purge got there, now a single collection-level error does. **This is a hit-rate increase caused by a fix, not an independent regression** — the fix is right and the consequence is real, so this moves up the queue rather than waiting its turn among the other seven.

- **PURGE-001 · The account-purge tombstone is retained identity data with no stated retention period** — raised 2026-08-09 from the production verification of #2228. `completePurgeJob` marks a finished job `status: "done"` and keeps it, which is the right call: a cleared tombstone would leave no durable guard against a late client resurrecting the profile with a still-valid cached token, re-opening the exact window #2228 closes. The consequence is that `accountPurgeJobs` grows **one permanent document per deleted account**, holding a `uid` and an `emailHash`. Hashed, and defensible on that basis — but it is retained identity data about a user who asked to be erased, and "we keep a hash of your address for ever" is a retention decision that has not been made or written down. Firebase ID tokens cap at an hour, so **24 h of guard is generous** and is the number to write down.

  The trap in doing that naively: the tombstone is quietly doing a SECOND job — it is also the only record that the deletion happened. TTL the document at 24 h and the audit trail goes with it. The two want splitting: a short-lived guard keyed on uid, and a durable deletion record. And it is worth asking whether the surviving record needs `emailHash` at all — the uid alone identifies the event, and the hash exists to recognise re-registration of the same address, which is a different feature with its own retention argument. **Not a defect in the fix** — a consequence of it that nobody has signed off.

- **PURGE-002 · `attempts` never increments on the happy path** — same source. A completed job carries `attempts: 0`, because `openPurgeJob` initialises with `increment(0)` and only `recordPurgeFailure` increments. That is internally consistent, but it means the counter reads as "failures", not "attempts", while being named the second thing — and `ALERT_AFTER_ATTEMPTS` reads it as the alert threshold. Once failures start landing in there, anyone reasoning about retry accounting has to know that a job showing `attempts: 3` has been tried three times and failed three times, while one showing `attempts: 0` has been tried once and succeeded. Rename or re-document; the Codex findings about sweeper retry behaviour are harder to reason about until it is one or the other.


- **PASSKEY-001 · Two flaws inherited from the passkey rollout, found while copying it** — surfaced 2026-08-06 by Codex review of #2130 (the Assessment Engine flag plumbing), which modelled itself on the passkey rollout as `docs/phase3-plan.md` §4.1 directs. Both were verified against the passkey code, not assumed from the copy; both are fixed on the engine's side and left open here so the passkey work inherits them deliberately rather than by accident.
  - **`passkeyRolloutUids` / `passkeyRolloutRoles` cannot be edited through the advertised path.** `settingsRegistry.js` documents them as "arrays, edited via config JSON", but `settingsCore.js`'s `normalizeSettings`, `exportConfig` and `validateImport` all traverse `allFields()` — the registry and nothing else. An unregistered key is therefore **silently dropped on import and absent from every export**, so the staged-rollout step those arrays exist for cannot be performed in the Platform Control Center at all. (Non-issue: `AdminSettings.jsx` saves with `setDoc(…, {merge: true})`, so a value written by other means is not destroyed by a settings save.) The engine's equivalent is now a registered `textarea` whose resolver accepts both text and an array; the same shape would work here.
  - **`featureFlags.passkeyAuthenticationEnabled` is not fail-closed against a dead listener.** `PlatformSettingsContext`'s `onSnapshot` error callback warns and sets `loaded = true` but leaves the last settings object in place, and Firestore does not resume a listener after `onError`. A client whose subscription dies after a successful snapshot therefore keeps the last value **indefinitely**, so disabling passkeys cannot reach it until the page reloads — contradicting the fail-closed property `passkeyService.js:242` and `PasskeySection.jsx:34` both rely on. `settings/global` is world-readable (`firestore.rules:585-588`), so this is a terminal-failure path rather than a routine one, but the guarantee is still false as stated. Fix belongs in the context (expose subscription health) rather than at each consumer.

- **AI-004 · Client-side Firebase AI Logic fails on quota (two teacher features broken, in two different ways)** — found in the 2026-08-05 console review ([`docs/security/AUDIT_LOG.md`](docs/security/AUDIT_LOG.md)). `firebasevertexai.googleapis.com` served **one production request in six weeks and it returned 429**; no paid quota appears to be configured on the AI Logic path. The two consumers are `src/utils/timetableExtraction.js` (timetable extraction) and `src/utils/forecastResourceSuggest.js` (weekly-forecast resource suggestions) — both reach Gemini via `src/utils/aiLogic.js` → `src/firebase/ai.js`. **The failure is not the same on both, checked against the error paths rather than assumed:**
  - `forecastResourceSuggest.js:65-68` catches, `console.warn`s, and returns `{ teacherResources: [], learnerResources: [] }` — a genuinely **silent** failure. The teacher sees empty suggestions and no indication anything went wrong.
  - `timetableExtraction.js:342-346` catches and **throws a user-facing message** — so it is *not* silent, but the message it throws is *"Could not read the timetable. - **FLAKE-001 · IDENTIFIED AND FIXED 2026-08-09 (#2216)** — the entry below concluded "not reproducible, environmental, no code change warranted". That conclusion is **superseded**: the failure was `LessonPlayer.spec.jsx > LessonPlayer — resume progress > persists the current slide as the learner advances`, it reproduces at **2 failures in 8 runs**, the cause is in test code, and it is fixed.
  **Cause:** the ArrowRight listener is registered in a passive effect (`LessonPlayer.jsx:145-156`), which React flushes *after* the commit `findByText` observes. The test awaited the counter — proving the DOM was painted and nothing about the listener — then fired the key into that gap, where nothing was attached to receive it. Key dropped, `index` stayed 0, persisted `{index: 0}` → `expected +0 to be 1`. **Not a product bug:** that gap is milliseconds between paint and effect flush, and the worst case for a learner who hit it is one ignored keypress.
  **Fix (#2216):** wait for the first progress write, which happens in the commit *after* the one that attaches the listener, so it is observable proof the listener is live. 24/24 green after, against 6/8 before; mutation-controlled by removing `goNext()` and confirming the test still fails with the original assertion.
  **How confident, honestly:** the identification is strong but circumstantial, and cannot be proved — the whole point of the original entry is that the identifying detail was discarded. What matches: same date, and the exact counts `1 failed | 3788 passed` of 3789, which is this suite with precisely one test failing. What does not contradict it: the 30× / 8× investigation below cleared `DailyExamRunner.spec.jsx` specifically and ran the full suite only 8 times — at a ~25% per-run rate for **this** test that is a ~10% chance of eight clean runs, unlikely but far from impossible, and the isolation runs were pointed at the wrong file. Treat as very likely the same failure, not certain.
  **The lesson below still stands and is the durable part:** the counts are the least useful part of a suite's output; write the run to a file rather than tailing it. Had that been done on 2026-08-09, this would have been a ten-minute fix instead of 30,822 test executions against the wrong suspect.
