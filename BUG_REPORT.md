### Still open

- **PASSKEY-001 · Two flaws inherited from the passkey rollout, found while copying it** — surfaced 2026-08-06 by Codex review of #2130 (the Assessment Engine flag plumbing), which modelled itself on the passkey rollout as `docs/phase3-plan.md` §4.1 directs. Both were verified against the passkey code, not assumed from the copy; both are fixed on the engine's side and left open here so the passkey work inherits them deliberately rather than by accident.
  - **`passkeyRolloutUids` / `passkeyRolloutRoles` cannot be edited through the advertised path.** `settingsRegistry.js` documents them as "arrays, edited via config JSON", but `settingsCore.js`'s `normalizeSettings`, `exportConfig` and `validateImport` all traverse `allFields()` — the registry and nothing else. An unregistered key is therefore **silently dropped on import and absent from every export**, so the staged-rollout step those arrays exist for cannot be performed in the Platform Control Center at all. (Non-issue: `AdminSettings.jsx` saves with `setDoc(…, {merge: true})`, so a value written by other means is not destroyed by a settings save.) The engine's equivalent is now a registered `textarea` whose resolver accepts both text and an array; the same shape would work here.
  - **`featureFlags.passkeyAuthenticationEnabled` is not fail-closed against a dead listener.** `PlatformSettingsContext`'s `onSnapshot` error callback warns and sets `loaded = true` but leaves the last settings object in place, and Firestore does not resume a listener after `onError`. A client whose subscription dies after a successful snapshot therefore keeps the last value **indefinitely**, so disabling passkeys cannot reach it until the page reloads — contradicting the fail-closed property `passkeyService.js:242` and `PasskeySection.jsx:34` both rely on. `settings/global` is world-readable (`firestore.rules:585-588`), so this is a terminal-failure path rather than a routine one, but the guarantee is still false as stated. Fix belongs in the context (expose subscription health) rather than at each consumer.

- **AI-004 · Client-side Firebase AI Logic fails on quota (two teacher features broken, in two different ways)** — found in the 2026-08-05 console review ([`docs/security/AUDIT_LOG.md`](docs/security/AUDIT_LOG.md)). `firebasevertexai.googleapis.com` served **one production request in six weeks and it returned 429**; no paid quota appears to be configured on the AI Logic path. The two consumers are `src/utils/timetableExtraction.js` (timetable extraction) and `src/utils/forecastResourceSuggest.js` (weekly-forecast resource suggestions) — both reach Gemini via `src/utils/aiLogic.js` → `src/firebase/ai.js`. **The failure is not the same on both, checked against the error paths rather than assumed:**
  - `forecastResourceSuggest.js:65-68` catches, `console.warn`s, and returns `{ teacherResources: [], learnerResources: [] }` — a genuinely **silent** failure. The teacher sees empty suggestions and no indication anything went wrong.
  - `timetableExtraction.js:342-346` catches and **throws a user-facing message** — so it is *not* silent, but the message it throws is *"Could not read the timetable. Try a clearer photo, or upload a PDF / Excel version."* On a 429 that message is **actively misleading**: it blames the teacher's file for a quota problem and sends them off re-photographing a timetable that was never at fault. Arguably worse than silence.
  Low blast radius (one request in six weeks) but two real broken features, and the second needs its error path to distinguish a quota/transport failure from an unreadable file. **Do not fix the quota in isolation:** making this path work also makes an *unmetered client-side* AI path operational, which is RISK-4. The routing decision — server-side Cloud Functions AI stack vs. client AI Logic — is tracked as P1-c in [`docs/architecture/25-remediation-plan.md`](docs/architecture/25-remediation-plan.md) and should be settled before or alongside the quota fix.
- **OBS-001 · Frontend crash reporting + APM** — CODE-COMPLETE 2026-08-01; residual is an operator step. Doc 11's snapshot is stale: `src/utils/sentry.js` already wires Sentry error reporting **and** APM (`Sentry.init` with `browserTracingIntegration()` at `tracesSampleRate: 0.1`), DSN-gated + tree-shaken when `VITE_SENTRY_DSN` is unset, and hidden source maps upload only when `SENTRY_AUTH_TOKEN` is present (`vite.config.js`). There is no code work left — Firebase `getPerformance()` would be redundant with Sentry browser-tracing. CI wiring: `${{ secrets.VITE_SENTRY_DSN }}` is passed by `deploy-hosting.yml` **and** the three Android workflows, so error reporting is wired everywhere. Source-map upload was web-only — `maybeSentryPlugin` (`vite.config.js`) returns no plugin unless `SENTRY_AUTH_TOKEN` + `SENTRY_ORG` + `SENTRY_PROJECT` are all present, and no Android workflow passed them, so Android release frames stayed minified. **Fixed 2026-08-01**: both *release* workflows (`android-release.yml`, `android-play-release.yml`) now pass the three build-time secrets. `android-debug-apk.yml` deliberately does NOT — it is designed to build with no secrets, and a debug build's maps would otherwise be uploaded under the same production release name as the shipped web/Android bundles. Web and Android builds do share a release (`zedexams@{version}-{mode}`, since both run `npm run build`), which is fine: `@sentry/vite-plugin` injects per-artifact debug IDs, so maps are matched by build rather than by release name alone. Also not checkable from the tree: whether the `VITE_SENTRY_DSN` secret **holds a value** (GitHub secrets are write-only).
- **TEST-001 · Authenticated end-to-end journeys** — needs a test harness that does not yet exist. The only browser test today is `scripts/test-mobile-smoke.mjs` (public pages: `/`, `/login`, `/register`, `/papers`, `/pricing`), and there is **no Firebase Auth emulator wiring anywhere** in the repo (`connectAuthEmulator` appears nowhere). A signed-in journey (dashboard → generate → save/export) therefore requires new CI infrastructure: boot the Firestore/Storage **and Auth** emulators in a CI job, seed a test user, point a Playwright run at them, and keep it non-flaky. That is a standalone infra project, not a code-only change, and it should land with owner review of the CI cost/shape rather than be auto-added as a (potentially flaky) gate. **Recommendation:** a dedicated non-required `e2e` job first (emulator + one seeded learner + one seeded teacher journey), promoted to required only once stable.
- **DATA-001 · `schoolId` multi-school model** — partial foundation exists; full rollout is architectural and must not be auto-migrated. `schoolId` is already threaded through the newer library data layer (`saveLibraryDocumentCore.js`, `lib/library/queries.js`, `teachingProfileCore.js`, cache/pagination keys) and appears in ~35 `firestore.rules` places. Completing it — `schoolId` on every core collection + cross-school admin aggregation + a backfill of existing docs — is a live-production data-model change plus a migration, which needs a design decision (tenancy model, rules impact, backfill/rollback plan) and owner sign-off. **Not safe to perform autonomously against a live database.** Left as a documented design item.

- ~~**AI-003 · No text content-moderation on learner-facing AI paths**~~ — RESOLVED 2026-08-01. Doc 07's snapshot (High severity: "only guardrail is a system prompt") is **stale** — a deterministic moderation layer over OpenAI omni-moderation was since added: `functions/contentModerationCore.js` (`evaluateModeration`/`decideContentOutcome`, blocked-category policy, env `MODERATION_FAIL_CLOSED`) + `functions/contentModeration.js` (`checkLearnerText`, `LEARNER_BLOCK_MESSAGE`), both tested. Wiring: the `aiChat` callable moderates **input and output**, `checkShortAnswer` moderates the learner answer, and `apiAiChat` moderated **input** — plus deterministic child-safety screening (`screenLearnerMessage`) ahead of the model on both chat paths. The one remaining gap closed here: `apiAiChat` (the SSE path the SPA uses) streamed model **output** un-moderated. It now accumulates the reply, runs `checkLearnerText` on it, and sends the screened text (or `LEARNER_BLOCK_MESSAGE`) as a single chunk — the client already supports a single-chunk reply (its Android SSE fallback), so output is moderated **before display**, matching the callable. Trade-off: token-by-token streaming on that path is replaced by a brief buffer then the full reply (the safety-correct choice for a child-facing path; an incremental-moderation design could restore live streaming later). A `chat_output_moderated` log line (with `rid`, OBS-003) records blocks.

- ~~**STOR-003 · No upload content/magic-byte verification**~~ — RESOLVED 2026-07-31 across the client upload/import surface. Every upload path validated only the client-declared `file.type`, which is forgeable (a script renamed `logo.png` passed an `image/png` allow-list, and a disguised `.docx` reached the ZIP parser — the SEC-007 concern; doc 06/18). Reusable verifier `src/utils/fileSignature.js` (`sniffMimeFromBytes` pure detection for PNG/JPEG/WebP/GIF/PDF/ZIP-OOXML/OLE2 + async `assertFileSignature(file, allowed)` that reads the real leading bytes and throws `file-signature-mismatch`; conservatively no-ops when it can't model any allowed type, so it never loosens the existing check; OLE2 detection means legacy `.doc/.xls/.ppt` validate rather than falsely reject). **Adopted at every untrusted client upload/import chokepoint:** picture bank, teacher branding, notes (image + doc), admin syllabus + curriculum panels, the quiz/paper **document+image import parser** (`importQuizDocument` — verified BEFORE fflate/mammoth/pdfjs touch the file), the four image-attach handlers in **CreateQuizV2** and **EditQuizV2**, and **LessonEditor**'s two `.pptx` handlers. Intentionally NOT wired: paths that upload an app-GENERATED blob rather than an untrusted user file (`visualAssetService`, `paperFigureAttach` crops, `quizDocumentImport` extracted images) — the source file was already verified. Tests: `fileSignature.test.js` (`test:file-signature`), `pictureBankService.spec.js` "real bytes are not an image", `documentQuizImporter.docx.spec.jsx` "rejects a non-document payload disguised as .docx". `storage.rules` content-type + size caps remain the server-side backstop; a Storage-triggered server scan (belt-and-braces, all paths server-side) is the heavier future option noted in doc 06.
